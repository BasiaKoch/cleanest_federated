                                              Abstract
The first detection of gravitational waves (GWs) from a binary neutron star (BNS) merger marked
the beginning of the multi-messenger era in astronomy. Traditionally, matched filtering (MF) has
been used to identify quiet GW signals buried in detector noise. The high computational cost of
MF-based algorithms impose a constraint on real-time GW searches, where a prompt alert is crucial
for follow-up searches of electromagnetic counterparts. The authors of [1] introduce a novel deep
learning (DL) algorithm that is optimised to detect GW signals from BNS mergers in long time
series strain data from a detector network. Based on the reproduction study presented in this
work, the neural network (NN) achieves a sensitive distance of 135 Mpc at a false alarm rate of 1 per
month for the Advanced LIGO design sensitivity. Compared to another competing NN, we achieve
a higher sensitivity at fixed false alarm rates. While the presented NN lacks the sensitivity of MF-
based search pipelines, it offers a superior latency of 10.2 seconds. We identified several challenges
with the original network architecture and training strategy, likely diminishing sensitivity and
increasing computational costs. To address these issues, we present a new NN with a simplified
architecture and training strategy and recommend training the NN with real detector noise and a
larger training set.

1      Introduction
The first detection of gravitational waves from the binary black hole (BBH) merger GW150914
in 2015 [5] with the Advanced Laser Interferometer Gravitational-wave Observatory (LIGO) [6]
was a groundbreaking event in the field of astronomy leading to the 2017 Nobel Prize in Physics.
Gravitational wave (GW) astronomy witnessed a series of subsequent detections originating from
BBH mergers [7, 8], with the event GW170814 [9] being the first detected by two LIGO detectors in
conjunction with the Advanced Virgo detector [10].

Multi-messenger Astronomy
The multi-messenger era in astronomy started with the detection of both GW signals and electro-
magnetic (EM) counterparts from the binary neutron star (BNS) merger event GW170817 [11, 12].
The short gamma-ray burst GRB 170817A [13, 14] was detected by NASA’s Fermi Telescope [15]
and ESA’s INTEGRAL [16] only seconds after the associated GW signal detection by LIGO and
Virgo. Optical and infrared counterparts were detected hours later by the Swope Supernova Sur-
vey 2017a and Hubble Space Telescope [17, 18, 19]. Weeks later, the Chandra X-ray Observatory
[20] detected the X-ray afterglow [21] of the GW event and several radio telescopes identified
a radio counterpart [22]. The simultaneous detection and analysis of GW signals and their EM
counterparts, known as kilonovae [23], provides a more comprehensive understanding of the as-
trophysical context of compact object mergers [24, 25, 26] and enables their precise localisation in
the sky [27]. Upon a positive GW detection, an automated alert system can be triggered to rapidly
notify observational telescopes worldwide to search for the EM counterpart. The success of detect-
ing EM counterparts is heavily dependent on the latency of the response. Ongoing improvements
in LIGO’s and Virgo’s sensitivity and KAGRA [28, 29] joining the GW detector network will con-
tinue to increase the detection rate of GW events [30]. In the future, GW astronomy will benefit
from a worldwide network of interferometers increasing the potential to extract further informa-
tion about the physics of compact object mergers with follow-up studies of EM counterparts with
current and upcoming astronomical facilities like the Vera C. Rubin Observatory [31].

Matched Filtering
Currently used algorithms in search pipelines like PyCBC Live [32, 33, 3, 34] use matched filter-
ing (MF) [35] to identify GW transients. These MF methods [34, 36, 37, 38, 39] use a template bank
which includes waveforms [40, 41, 42, 43, 44, 45, 46] each with different model parameters. As these
parameters are not known a priori, these template banks cover a large parameter space currently
available to GW detectors. The full 9-dimensional parameter space includes the binary component
masses m1 and m2 , two 3-dimensional spin vectors s1 and s2 and the orbital eccentricity e [47].
Moreover, parameter estimations studies in GW astronomy require an even larger, 15-dimensional
space [48]. As our understanding of compact binary mergers deepens, the development of more ac-
curate waveform models increases, leading to a growth in the number of models within template
banks. However, the computational costs of MF-based searches directly scale with the template
bank size. Low-latency GW searches with MF currently only sample from a 4-dimensional param-
eter space (m1 , m2 , s1z , s2z ), i.e. spin-aligned binary masses on circular orbits [49]. This is because
the extension of these algorithms to the full parameter space is unfeasible given their computa-
tional cost [50]. MF-based searches targeting the aforementioned 4-dimensional parameter space
may miss GW events from BNS mergers or BH-NS mergers [4], where a prompt alert is crucial for
the observation of their EM counterpart. Therefore, there is a rising need to tackle the computa-
tional limitations of current GW detection pipelines. Additionally, reducing the number of false
alarms is crucial due to the high cost associated with the observing time needed to search for EM
counterparts [1].

Deep Learning
To harness the full potential of multi-messenger astronomy, it is crucial to deploy algorithms capa-
ble of detecting and analysing GW events in real-time [51] and in the full parameter space of ex-
isting and upcoming GW detectors [4]. Deep learning (DL) [52] approaches have recently gained
attention in GW science [53, 54, 55]. DL is a branch of machine learning (ML) that uses neural
networks (NNs) with multiple layers to model complex patterns in data. Each layer consists of
neurons that are associated with learnable weights that help the model learn relationships between
input data and the desired output. During training, these algorithms adjust the weights to min-
imise the loss function, which measures the discrepancy between the predicted and actual results
in the case of supervised learning. Once the deep NN is trained, it can be used as a predictive tool
for various tasks such as regression or classification. Convolutional neural networks (CNNs) [56]
were proposed to search for GW signals from BBH mergers [57, 58, 59]. Similar DL models were
used to extend this concept to the detection of GW signals from BNS mergers [4]. A more com-
plex architecture involving inception modules [60] and temporal convolutional networks (TCNs)
[61] was designed to further improve BNS searches with ML [1]. Other ML applications to GW
science include glitch classification [62], [63], the search for continuous GW signals [63, 64], the
detection and classification of supernova GW signals [65, 66], denoising of BBH merger signals
[64] and GW parameter estimation [67, 68, 69]. NNs allocate most of the computational cost to
the training phase, prior to the actual prediction stage [70]. Once trained, their high evaluation
efficiency makes them attractive candidates for real-time GW searches from BNS mergers.

State-of-the-art Benchmarks
Existing low-latency searches with MF have a latency of O (10) seconds and a sensitive distance
of 250 Mpc at ∼1 false alarms per month [71, 72, 73]. For an alternative search algorithm to be
competitive, it must meet or surpass these performance criteria [1]. At high false alarm rates (FARs)
and signal-to-noise ratios (SNRs), CNNs designed for BBH merger searches [57, 59] show similar
sensitivity performance to MF methods at a significantly lower computational cost. These NNs are
designed to detect signals from BBH mergers only. In the context of multi-messenger astronomy,
rapid notifications to other observatories are most useful and relevant for GW signals from BNS
mergers. Signals from BNS mergers are much more challenging to detect using DL than signals
from BBH mergers. The NN presented in [4] was tested at an estimated FAR of ∼8500 per month.
The sensitivity results of the search algorithm for BNS merger signals in [1] were obtained at FARs
down to ∼10 per month, and its latency is estimated to be 10.2 s. However, in order for these NNs
to be considered superior to existing methods, they must undergo further testing with real detector
data at the required FAR of ∼1 per month.

Objectives
The primary objective of this work is to reproduce the results presented in [1], hereafter referred to
as the original work. However, this work extends the original work by (i) including a number of
new performance metrics, (ii) optimising search hyperparameters, (iii) testing the existing network
at lower FARs and (iv) proposing an improved network architecture and training strategy.

Structure of Thesis
The structure of the report is as follows: Chapter 1 serves as an introduction to existing literature
on GW searches with MF and DL. Chapter 2 details the methods used in this work. This includes
the data processing, data representation, GW search metrics and GW search algorithms. Chapter
3 presents the performance results based on the previously introduced GW search metrics. In
Chapter 4, we discuss these results in the context of GW science, multi-messenger astronomy and
DL. Finally, we provide conclusive remarks and identify areas of future work.

2.1     Data Processing
GW detectors have two kilometer-long arms forming an L-shape. When a GW from a BNS merger
passes through Earth, it stretches one arm and compresses the other. This minuscule change in
the relative arm lengths is measured using laser interferometry. A laser beam hits a beam splitter,
sending light down each arm to mirrors that reflect it back. These mirrors reflect the beams back to
the beam splitter, where they interfere with each other. If the arm lengths are unchanged, the light
waves cancel each other out, while a change of the path lengths leads to an interference pattern
registered by the detector. The small change in arm length, called strain, is measured over time,
resulting in a strain time series as the primary data product. In addition to GW signals, detectors
record arm length changes due to noise, which dominates the amplitude output [74]. The resulting
time-domain signal s(t) consists of the GW strain component h(t) and the noise component n(t):

                                            s ( t ) = h ( t ) + n ( t ).                                  (1)

2.1.1    Test Dataset
The performance of a GW signal search algorithm is best evaluated on long stretches of continuous
strain time series data. With only two detected GW signals from BNS mergers to date, we need to
simulate test data containing numerous GW signal injections buried in noise. Following a proce-
dure similar to [1], we generate a test set equivalent to one month of data (31 days), in contrast to
the three-month dataset in the original work [1]. Each day includes 21 simulated files, each 4096 s
long, resulting in 651 files. Each file is independently generated by using different random seeds.
A summary of this procedure is detailed below:
    1. We generate noise from the analytic estimate of the power spectral density (PSD) of the Ad-
       vanced LIGO design sensitivity [30] with the aLIGOZeroDetHighPower model in the soft-
       ware library LALSuite [75]. While real detector data contains non-Gaussian transient noise
       or blip glitches [76, 77], the simulated noise is stationary and Gaussian.
    2. Next, we generate a list of GW signal injection timestamps within the full duration of one file
       with the condition that the temporal separation of two consecutive injections is chosen from
       a uniform distribution within the interval (180, 220) s. To avoid incomplete waveforms, we
       discard injections within the first or last 256 s of each file. This results in 18 injections per file
       and 11,718 injections in total. For each of these timestamps, we generate a waveform using
       the inspiral-only waveform model TaylorF2 [42, 44, 78]. The lower frequency cutoff is set
       to 25 Hz, while the model parameters are drawn from the distributions specified in Table 1.
       These distributions are chosen to represent non-spinning BNS mergers with an isotropic sky
       distribution.
    3. While previous works only used data from a single detector [57, 59], we follow the approach
       in [1] and use data from two detectors. The waveforms are projected onto the operational
       frame of the LIGO-Hanford (H1) and LIGO-Livingston (L1) detectors [79] and added into
       the noise so that maximum amplitude of the GW signal aligns with the injection timestamps.
Figure 1 shows a 4096 s test file, while Figure 2 zooms in on a 32 s chunk showing one waveform.
During the application of the search algorithm on the test dataset, the data is also whitened as
detailed in Section 2.1.3.

2.1.2    Training and Validation Dataset

2.1.3    Input Data Representation
Unlike BBH signals, BNS signals last O(102 ) s in the detectors’ sensitive band [11]. Training a NN
with such large inputs sizes poses computational and optimisation challenges, making it practi-
cally infeasible to use the raw data as input to a DL algorithm [1]. Thus, it is necessary to find an
appropriate input data representation of the strain time series. The CNN in [4] takes the last 10 s
as an input to detect BNS-powered GW signals. However, this approach reduces the SNR within
the data, leading to a decreased search sensitivity. To reduce the input dimension of the NN while
preserving a high SNR, we adapt the multi-rate sampling approach from [1]:
  1. We whiten the data with the analytical PSD aLIGOZeroDetHighPower before resampling.
     Whitening in signal processing is a technique to transform a signal to have a flat spectrum,
     where each frequency component has equal power. It does this by reweighting each fre-
     quency bin with the average power of the background noise in that bin [1]. Note that the
     noise and signal samples are whitened individually during training and then added together.
     This is not possible for the test dataset, where we instead whiten the total strain with the same
     analytic PSD estimate used for the training and validation data [1].
  2. When applying the network to long data-segments, we use a sliding window approach as
     detailed in Section 2.2.2. After whitening, the final 32 s of the window are sampled at different
     rates depending on the strain evolution. Lower frequencies in the initial inspiral phase are
     sampled at lower rates, while higher frequencies in later phases are sampled at higher rates.
     TThe multi-rate sampling intervals and rates are detailed in Table 2 and visualised in Figure
     5. This gives 7 interval segments, each containing 2048 samples.

2.2     Gravitational Wave Search Metrics
In realistic scenarios, GW search algorithms process continuous strain time series containing de-
tector noise and potential GW signals. Adapting performance metrics for DL search algorithms,
which are trained and tested on discrete data, is challenging [53]. We present a strategy to address
this discrepancy for improved performance evaluations and comparisons.

2.2.1   Matched Filtering Searches

of a detection as either false positive or true positive is determined based on the simulated test

the level of confidence in the detection of an alarm produced by a search algorithm. The ranking
statistic R is the SNR, which is the output of MF-based searches as detailed in Section 2.3.

Sensitivity
The sensitivity S of a search algorithm is its ability to correctly detect true positive signals, defined
as the ratio of predicted true positives to actual true positives. For GW signals in the simulated
test set, this ratio is influenced by the parameter distribution of the injected signals [1]. Specific
orientations and greater distances reduce the amplitude and SNR of GW signals, making the de-
tection more challenging. A more informative measure of S is the sensitive volume V (Fthresh ) of
the search algorithm. If the GW signal injection distribution matches the expected sky distribution,
this metric can be approximated with:

to estimate V (dmax ). Both NTP (Fthresh ) and NFN (Fthresh ) represent detected and missed injections

Performance Evaluation Challenges
This performance evaluation approach presents a number of challenges discussed in [1, 53]. The
primary issues are summarised below:
   1. The maximum amplitude of GW signals in the training set are placed within a narrow range
      for efficient NN training, which may not reflect real data accurately. Thus, performance
      evaluations on such test sets may not be representative of real-world performance.
   2. GW search algorithms are applied to long, continuous time series of variable durations, while
      NNs require fixed-duration inputs. To handle longer time series, the NN can be applied
      by sliding over the time series with a fixed-size window and step size, as described in the
      following subsection. This approach may predict a signal at multiple successive positions,
      cause oscillations of signal predictions across consecutive positions, or capture only part of a
      signal. The notion of a true or false positive signal detection becomes unclear in this case.
To compute values for F and S for our NN, we use the test set from Section 2.1.1. This set contains
much longer data-segments than the training set, providing a more suitable basis for evaluation.

Sliding Window Approach
We apply the trained NN with a 72 s sliding window over the test time series as in [1]. To en-
sure signal sensitivity, the step size must be no larger than half the 0.5 s interval in which the
maximum waveform amplitudes are placed in the training set [1]. The step size is set to the up-
per bound of 0.25 s to balance sensitivity and computational efficiency, ensuring the network cap-
tures true signals without redundancy. Each window is whitened with the analytical PSD estimate
aLIGOZeroDetHighPower, as described in Section 2.1.3. The initial and final 4 s are excluded [1],
and the final 32 s of the remaining data are resampled, as detailed in Section 2.1.3.

Ranking Statistic
Instead of designing a NN with the binary outputs ’noise+signal’ and ’noise-only’, adopting a
continuous output enables us to use it as a ranking statistic R. For a specified ranking statistic
threshold Rthresh , we can find timestamps in the time series for which the NN predicts values of R
exceeding Rthresh , indicating the presence of a signal. The NN introduced in Section 2.4 predicts
the SNR and a p-score for the input time series, which can both be used as a ranking statistic R.

Clustering of Signal Candidate Events
In the original work [1], it is assumed that two signal candidate events occurring within 1 s of
each other belong to the same GW signal. However, this assumption is relatively arbitrary and we
choose an optimised value of 3.5 s for the clustering criterion1 , see Table 3. We cluster timestamps
for which R > Rthresh and define a signal candidate event in the following way:
   1. Flag the timestamps for which R > Rthresh .
   2. Cluster the flagged timestamps by (i) defining the neighbourhood of a flagged timestamp as
      within ±3.5 s of its occurrence, (ii) grouping all flagged timestamps within this neighborhood
      into the same cluster, and (iii) merging clusters based on overlapping neighborhoods.
   3. Each cluster represents a GW signal candidate event and is assigned the time and ranking
      statistic corresponding to the maximum R value within the cluster.

Inception Modules
After the amplified data is preprocessed by convolutional layers, an Inception block (lower left

connection. Inception modules are the building blocks of the deep CNN ‘Inception’ developed by

2.4.2   New Deep Neural Network
The complex design of the original architecture in Figure 7 and training strategy results in in-
creased computational costs and overfitting issues [1]. Therefore, we propose an alternative, sim-
pler network architecture design and training strategy.

Architecture
Below, we list a number of identified challenges associated with the complex architecture design
of the original network:
   1. Multiple Stack Network: The multi-rate sampling approach detailed in Section 2.1.3 is an
      innovative data representation we plan to adopt for the improved NN. However, the un-
      conventional method of handling different sampling intervals - analyzing each interval as
      a single stack and only concatenating later - may result in the loss of temporal continuity.
      Important temporal dependencies spanning interval boundaries might be missed, and tem-
      poral evolution patterns over longer spans, such as long GWs from BNS mergers, are not
      effectively captured when each interval is analysed in isolation. Additionally, this increases
      computational costs as each stack requires its own model layers and processing blocks.

                                                    13
2. METHODS                                                                 2.4. Deep Learning Searches


  2. Redundant and Auxiliary Outputs: The performance outcomes in the original work [1] and
     this study demonstrate that using the SNR estimate as a ranking statistic yields substantially
     better results than the p-score output [1]. For example, the p-score output is not able resolve a
     FAR of ∼1 per month, which is required to present a competitive alternative to MF. Moreover,
     these network outputs are highly correlated and redundant. This could adversely impact the
     optimisation of the network during training. The potential issues include more complex loss
     landscapes, inefficient and unstable training, and overfitting. Additionally, the numerous
     auxiliary outputs complicate the loss function and training of the network. More details on
     this problem are given in the alternative training strategy discussion.
  3. Complex Architecture Design: In addition to the points above, the use of Inception mod-
     ules also contributes to an overly complex architecture. Inception modules are designed to
     capture spatial relationships among pixels in images. However, our time series data is se-
     quential and temporal in nature, where the relationship between data points depends on
     their order and timing rather than spatial proximity. Adapting multiple Inception modules
     for time series inputs is not ideal. A simpler architecture could improve the latency and make
     the network more attractive for real-time searches.
Based on the identified challenges, we propose the following improvement suggestions for the
network architecture with an overview of the new NN shown in Figure 8:
  1. Single Stack Network: We propose to concatenate the interval segments after the first layer
     and then process the resulting stack as a whole in order to capture temporal and sequential
     dependencies more effectively and efficiently.
  2. Single SNR Output: Finally, we propose to only use the SNR as a ranking statistic and main
     network output in order to reduce overfitting issues and improve the optimisation of the
     network during training. This also aids in simplifying the network’s architecture and allows
     the search algorithm to be better comparable to the output of MF-based searches.
  3. Simplified Architecture Design: We adapt the TCN part of the network for denoising and
     signal amplification. Instead of Inception modules, we use a CNN block consisting of 1D
     custom convolutional layers to extract lower-dimensional features from the denoised input
     data. The CNN block is then followed by a recurrent neural network (RNN) block [86].
     RNNs are neural networks capable of processing sequential data like time series. Specifically,
     we propose a special type of RNN called Long Short-Term Memory (LSTM) [87], which is
     designed to handle long-term dependencies more effectively. Once the CNN layers extract
     features from the input, the RNN layers’ function is to capture the temporal dependencies in
     the sequence of extracted features. The proposed changes result in a simplified architecture.

Training
Below, we list a number of identified challenges with the training strategy of the original network:
  1. Training and Validation Split: The current training and validation set has a split of approxi-
     mately 96:4, which is rather unusual. With such a small validation set, less reliable feedback
     can be provided during the training process. This leads to ineffective parameter updates
     during training and a model that does not generalise well to unseen data.
  2. Unbalanced Training Set: The training set has 10:1 split between signal and noise samples.
     This unbalanced training set could bias the model toward the majority class leading to inef-
     fective learning from the minority class, higher FARs and skewed performance metrics.
  3. Loss Function and Overfitting: The authors of the original work [1] report strong overfitting
     issues during the training process. While the training loss fell by 25% from the first to last
     epoch, the validation loss grows throughout the training process by 75% from the first to last
     epoch. Moreover, they monitor the sensitivity of the model during training and find that the
     sensitivity is at best loosely correlated with the validation loss [1]. Both of these findings are
     highly counterintuitive and indicate that the proposed loss function is not well suited for the

       problem. The loss function includes the previously mentioned redundant p-score output and
       additional 13 auxiliary outputs, making the loss function overly complex.
Based on the identified training issues, we propose the following improvement suggestions for the
training strategy:
   1. Training and Validation Split: We propose a more commonly used split of 80:20 for training
      and validation. This improvement provides a more balanced feedback during training and
      should help improve performance estimation, parameter tuning and generalisation.
   2. Balanced Training Set: We propose a balanced split between signal and noise samples to
      avoid biases, improve performance metric calculations and reduce overfitting.
   3. Simplified Loss Function: Because we reduce the network output to a single SNR prediction,
      we propose the following simplified loss function:

                                                      L(ytrue , ypred ) = MSE(SNRtarget , SNRpred ).                                                                       (15)

       This will resolve the strong overfitting issues of the current training strategy, likely leading to

4      Discussion & Conclusion
4.1    Discussion
We discuss the findings of this work compared to the original work and the state-of-the art.

Comparison to the Original Work
The main methodological differences between this and the original work are:
    • We used a test set worth of approximately 1 month of data compared to 3 months in the
      original work. The waveform injections are also likely to be produces with different seeds.
    • We use optimised clustering and detection criteria compared to the arbitrary choices in the
      original work.
    • The exact calculation of the injected SNR is not provided in the original work. Hence, the
      implementation used in this work is likely different.
These methodological differences contribute to varying results, although to different degrees. The
main result, i.e., network sensitivity as a function of FAR in Figure 10, is very similar to the original
work, achieving similar sensitive distances at different FARs. This indicates good generalisation
across different test datasets, even smaller ones. Our optimised clustering and detection criteria
yield slightly better sensitivity results. The true positive rate at different injected SNRs in Figure
11 is higher in our work at fixed FARs. In the original work, the network only performs better than
the competing network by [4] for SNRs in the training range. In our work, the network performs
better than the competing network for higher SNRs, likely due to different implementations for the
injected SNR calculation. The predicted vs injected SNR in Figure 12 achieves a significantly lower
MSE than the one in the original work, again due to different SNR calculations. However, similar
to the original work, the SNR output is more successful in detecting signals than the p-score.

Comparison to the State-of-the-art
At a FAR of down to 1 per month, the NN is not competitive with the MF-based pipeline PyCBC
Live. This is likely due to insufficient variety of signal and noise combinations used during train-
ing. The computational cost of the NN is not superior to the MF due to the complex architecture.
However, the NN offers a superior latency of 10.2 s compared to an average latency of 16 s for
PyCBC Live.


4.2    Conclusion
We reproduced the NN-based search results for BNS signals from [1]. The network’s sensitivity
is superior to other ML algorithms for BNS signals, though it still not yet competitive with the
MF-based PyCBC Live. However, it offers superior latency. DL will be crucial for developing
real-time GW search pipelines to foster the full potential of multi-messenger astronomy. The com-
putational cost of MF scales with the size of the template bank used. Extending search algorithms
to the full parameter space will benefit from the lower computational costs and latency of NNs,
because most of the computational cost could be allocated to the training phase. Our work ex-
tends the original work by optimising the search hyperparameters, testing the network at lower
FARs and suggesting an improved network architecture and training strategy. Future research can
build on these findings to develop highly sensitive, low-latency pipelines for the data-driven dis-
covery of GWs and the prompt detection of their EM counterparts. Future work involves training
and applying the new network with the improved strategy on real detector noise and an expanded
training set for greater signal and noise variety. These improvements should reduce computational
costs and latency while increasing sensitivity closer to state-of-the-art levels. Another possible use
of DL might be the use of a simple low-latency NN at high FARs, followed by a MF-based search.

Description
This project is associated with the submission of the coursework for the Research Project as
part of the MPhil in Data Intensive Science at the University of Cambridge. The coursework
instructions can be found under Instructions.md. The associated project report can be found
under Project Report. The associated executive summary can be founder under Executive
Summary.

The primary objective of this project is to reproduce the results presented in
https://journals.aps.org/prd/pdf/10.1103/PhysRevD.102.063015. However, this work extends the
original work by (i) including a number of new performance metrics, (ii) optimising search
hyperparameters, (iii) testing the existing network at lower FARs and (iv) proposing suggestions
for an improved network design and training strategy.

Data Availability
The data used for this project is found here: Research Project - Submission Data. It includes the
following folders and files:

      datasets : Includes the files of the test dataset. It is split into 31 days of data, where 1
     day includes 21 of the following type of files: (i) strain data time series consisting of noise
     and signal injections (4096s per file), (ii) a corresponding injection statistics for each
     injection within the strain data file, (iii) the corresponding SNR output after the network is
     applied to the time series, (iv) the corresponding p-score output after the network is applied
     to the time series. It also includes combined files that are finally used to produce the project
     results. Please make sure to include this folder into the sd2022 directory, if you want to
     run the network on the test dataset used in this work and you do not want to regenerate it
     from scratch.
      results : Includes the final results data of the project. Please make sure to include this
     folder into the sd2022 directory, if you do not plan to run the entire analysis from scratch
     but are only interested in reproducing the final results.


Installation
To get started with the code base, follow these steps:


Requirements

     Python 3.9 or higher installed on your system.
     Conda installed (for managing the Python environment).
     Docker (if using containerisation for deployment).
     PyCBC 2.4 (for gravitational wave data analysis)
     Keras (TensorFlow) 2.12.0 (for neural network usage)

We recommend simply setting up the same environment (see environment.yml) as the one used
throughout this project. The instructions to set up this environment are shown in the Setup
section. If you decide to use your own environment, it is highly recommended to install PyCBC
with the following command:


 pip install pycbc ligo-common --no-cache-dir
Setup

Local Setup (Without Docker)

 1. Clone the Repository:

    Clone the repository to your local machine with the following command:


     $ git clone https://gitlab.developers.cam.ac.uk/phy/data-intensive-science-mphil/pr


    or simply download it from Research Project (sd2022).

 2. Navigate to the Project Directory:

    On your local machine, navigate to the project directory with the following command:


     $ cd /full/path/to/sd2022


    and replace /full/path/to/ with the directory on your local machine where the
    repository lives in.

 3. Setting up the Environment:

    Set up and activate the environment with the following command:

     $ conda env create -f environment.yml
     $ conda activate ml4gw


 4. NOTEBOOKS ONLY: Install ipykernel:

    To run the notebook cells with ml4gw , install the ipykernel package with the following
    command:


     python -m ipykernel install --user --name ml4gw --display-name "Python (ml4gw)"


Using Docker (Recommended for Containerised Deployment)

 1. Clone the Repository:

    Clone the repository to your local machine with the following command:


     $ git clone https://gitlab.developers.cam.ac.uk/phy/data-intensive-science-mphil/pr
   or simply download it from Research Project (sd2022).

2. Navigate to the Project Directory:

   On your local machine, navigate to the project directory with the following command:


    $ cd /full/path/to/sd2022


   and replace /full/path/to/ with the directory on your local machine where the
   repository lives in.

3. Install and Run Docker:

   You can install Docker from the official webpage under Docker Download. Once installed,
   make sure to run the Docker application.

4. Build the Docker Image:

   You can build a Docker image with the following command:

    $ docker build -t [image] .


   and replace [image] with the name of the image you want to build.

5. Run Notebooks or Scripts:

   For the notebooks, use the following command:

    $ docker run -p 8888:8888 [image]


   This command starts a container from the [image] image and maps port 8888 of the
   container to port 8888 on your local machine. The Jupyter Notebook server within the
   container will be accessible on JupyterLab at http://localhost:8888.

   For the scripts, use the following command:

    $ docker run -it --name=[container] [image]


   and replace [container] with the container name and [image] with the image
   name you created. And then simply run the scripts described in Usage.
Usage

Neural Network Model

The repository includes the trained neural network in the sd2022/models directory:
network.hdf.


Notebooks

The repository includes the following notebooks in the sd2022/src directory:

 1. Demonstration Notebook - a demonstration of the different analysis steps on a single test
     file including visual aids: DEMO.py
 2. Results Notebook - a collection of results and the associated plots: RESULTS.py


DEMO.py Notebook

This notebook includes a demonstration on how to: - generate a test data file, i.e. a strain time
series with waveform injections buried in noise - apply the neural network to the test file, i.e.
predict the SNR and p-score time series - detect events based on ranking statistic (SNR/p-
score) thresholds

It produces a number of plots shown in the Methods section of the project report.

RESULTS.py Notebook

This notebook includes the following project results: - False alarm rate as a function of the
ranking statistic thresholds - Sensitivity as a function of the false alarm rate - Predicted vs
Injected SNR - True positive rate for different injected SNR bins

It produces a number of plots shown in the Results section of the project report.

NOTE: Please make sure the following files are included in the sd2022/results directory: -
results1snr4.0:0.2:40.0cluster3.5tol3.0.csv - results1psc0.01:0.01:1.0cluster3.5tol3.0.csv -
results2snr4.0:0.2:40.0cluster3.5tol3.0.csv - results2psc0.01:0.01:1.0cluster3.5tol3.0.csv

They can be obtained from Research Project - Submission Data or by reproducing the entire
project results from scratch by following the steps in the next section.


Local Usage (Without Docker)
Open the sd2022 directory with an integrated development environment (IDE), e.g. VSCode
or PyCharm, select the kernel associated with the ml4gw environment and run the Jupyter
Notebooks (located in the sd2022/src directory).


Using Docker (Recommended for Containerised Deployment)

After running the container in Step 5 in Installation, you'll see logs in the terminal containing a
URL with a token. It will look similar to this:


 http://127.0.0.1:8888/lab?token=XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX


Navigate to http://localhost:8888 and enter the token
 XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX . Once you accessed JupyterLab,
run the Jupyter Notebooks(located in the sd2022/src directory) with an ipykernel
(Python 3).

NOTE: Make sure that no other Jupter Notebook Servers are running. Otherwise, you might
encounter 'Invalid credentials' issues when entering the token. Close any running Jupter
Notebook Servers. To stop a running server, use Ctrl + C in the terminal where you
launched JupyterLab. Also make sure port 8888 is not occupied.


Scripts

The repository includes the following main scripts in the sd2022/src directory:

 1. Data Generation - generate test data: run_data_generation.py
 2. Network Prediction - apply the neural network to test data and predict the SNR and p-score:
     run_ts_prediction.py
 3. File Manipulation - reconfigure and combine the prediction files: run_file_manipulation.py
 4. Event Detection & Performance Evaluation - detect events in the combined prediction file
     based on different ranking statistic thresholds & evaluate the performance of the network
     on the test data with several performance metrics: run_detect_evaluate.py


Local Usage (Without Docker)

Simply run the scripts described above within the sd2022/src directory.


Using Docker (Recommended for Containerised Deployment)

After running the container in Step 5 in Installation, simply run the scripts described above within
the sd2022/src directory in the Docker container.
Data Generation

For the data generation, run the following command:


 $ python run_data_generation.py [folder_path] [duration] [total_runs] [day]


      [folder_path] : The path to the folder where the test data files will be saved.
      [duration] : The duration of the test data files (in seconds).
      [total_runs] : The total number of files to generate.
      [day] : The day for which the files will be generated. Important to set different seeds for
    each day.


Network Prediction

For the network prediction, run the following command:

 $ python run_ts_prediction.py [folder_path] [model]


      [folder_path] : The path to the folder where the test data files will be saved.
      [model] : The duration of the test data files (in seconds).

File Manipulation

For the file manipulation, run the following command:

 $ python run_file_manipulation.py [folder_path] [n_days] [files_per_day]


      [folder_path] : The path to the main data folder containing the generated files.
      [n_days] : The number of day folders within the main data folder for which the files
    were generated.
      [files_per_day] : The number of files generated per day.


Event Detection & Performance Evaluation

For the event detection and performance evaluation, run the following command:


 $ python run_detect_evaluate.py [ranking_ts_path] [injection_stats_path] [threshold_st


      [ranking_ts_path] : The path to the combined ranking time series file.
      [injection_stats_path] : The path to the combined injection statistics file.
      [threshold_start] : The starting ranking statistic threshold value.
      [threshold_end] : The ending ranking statistic threshold value.
      [threshold_step] : The ranking statistic threshold step value.
      [cluster_criterion] : The cluster criterion value (in seconds).
      [detection_criterion] : The detection criterion value (in seconds).

 $ python run_ts_prediction.py [folder_path] '../models/network.hdf'


with [folder_path] being '../datasets/day1/', '../datasets/day2/', ..., '../datasets/day31/'.
1. File Manipulation:

$ python run_file_manipulation.py '../datasets/' 31 21

 $ doxygen

 $ make
